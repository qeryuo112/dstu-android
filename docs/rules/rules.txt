项目开发原则
1.项目开发严格按照计划文档分阶段进行，每一轮开发需全部完成，才能汇报。即每轮开发，相应计划必须全部完成，不能做一半，留一半。
2.项目开发需记录准确的文档，每轮开发完成，均要写交接文档，同时标注准确的系统时间。且文档只能以追加方式修改，除非之前表述确实存在错误。
3.开发时，每轮均要测试，完成后才能汇报。同时，每一小轮结束后，需要 Git 提交到本地，方便出问题回溯。
4.开发时，在功能实现的代码之外，还要添加详细日志，方便调试。
5.每轮开发完成，请整理工作区，文件夹应保持干净，仅有源码，最终调试日志，文档。无中间产物。文档仅保留最后的交接文档。子智能体产生的中间日志，文档和截图应该清理。最终调试日志和验收截图归档到仓库外的 artifact 存储；Git 仅保留证据索引、校验和及使用说明，不追踪 logs/ 原始文件。构建缓存和临时测试输出必须被忽略，不得提交。
6.开发过程中，主智能体进行审查，测试，对开发最终结果负责，充当大脑的作用。子智能体负责探索，修改大部分代码，充当手的作用。尽量使用子智能体协助开发。（请严格遵守这项规则）
7.每个子智能体仅完成被分配的当前单元，不得跨单元继续工作。进入下一单元必须新建子智能体，例如S0.18的子智能体不得继续S0.19。
8.最新执行调整：同一阶段的不同单元可分配独立子智能体并发，最多3个；一个智能体只负责一个单元。同单元会话数量不限。主智能体按依赖顺序集成、独立测试、交接及本地提交，阶段出口仍须等待本阶段全部签收。
9.计划文档允许直接替换相关行；交接文档继续按准确系统时间追加。桌面基线冻结于本次同步的e6b2657fd59014a73f5bbb1d14c2db732cf23e87，后续不再跟进上游，仅以该提交桌面功能为重写目标，不采用其自带安卓运行链。
10.按照计划顺序进行开发，虽然可以并行使用子智能体，但单元间必须是前置完成，才能接入主线，禁止提前集成。
11.用户是一名比较业余的开发者，需要你在实现过程中说明自己完成了什么，不能一味的埋头苦干，这样用户不知道你干了什么，你可以把用户理解为许愿式编程。同时，禁止防御性语句。在遵循上述规则的同时，项目开发禁止偷懒，不能为了省事糊弄用户，而是要严格实现需求。
12.dstu-android本质上是dstu-node安卓部分的原生重构，最终交付是具有完整冻结dstu-node桌面功能的Android原生端，不是精简版、伴侣端或只覆盖部分功能的移植版。必须与冻结桌面基线e6b2657fd59014a73f5bbb1d14c2db732cf23e87保持业务语义、共享数据schema、同步wire和备份恢复兼容；平台差异使用Android原生适配实现，不擅自删除桌面功能，也不另造不兼容协议。不采用上游旧Android运行链，不等于缩减桌面功能。
13.每个新单元或功能开工前，主线程和专属子智能体必须先核对冻结版本，并阅读/home/xutao/deepstudent/dstu-node和/home/xutao/deepstudent/Operit中与该功能相关的实现、调用链和测试；Operit冻结于7a39941bad80209973c535046a18195c5da9e647，terminal冻结于e4646680663789002b43bbfffa6e69e65c35e614。记录相关路径、关键合同、可复用设计及差异后才可开发，不能只读交接文档、摘要或自己旧代码，也不自动追新上游。若某一侧没有对应实现，必须记录实际搜索范围和最接近的相关组件，不得臆造；Operit不是dstu多端同步协议的来源。用户是业余开发者，说明要直白，禁止防御性套话。
14.子智能体中断或未交付可核验结果时，主智能体先检查已落盘成果，再为同一单元新开子智能体接续。每个单元在首次尝试之外最多重试三次；三次重试仍未完成，才由主智能体接手。重试沿用原写入范围、前置依赖和并发上限，不撤销有效改动，不绕过明确的权限或安全限制。
15.后续开发禁止新建 Git 分支。本地 main 为开发、集成和验证基线，不为单元、子智能体或候选验证另建开发分支。前置依赖、正式接入、验收、证据与本地提交要求不变；合入本地 main 不代表推送远端。
16.此文档为最重要文档，压缩上下文（compact）时需保留信息，每轮开发均先阅读该文档。
