# 真机验证与签收前置

自 2026-11-24 起，执行身份、授权和依赖设备权限的实测按下表分工。**先确认测试设备和实际权限，再执行对应的用例；两台设备不要求拥有相同的权限上限。**

| 设备 | 用户环境 | 最高权限档 | 签收时的判据 |
| --- | --- | --- | --- |
| **V2232A 手机** | 普通用户；无 Root | **Operit 五档的第四档：Shizuku 配对并启动后的 ADB 调试权限** | 用户授权隔离测试包后，`SHIZUKU` 走实际服务，核对后端与命令实测 UID 均为 `2000`（`shell`）。`ROOT` 正向用例不适用；有 Root 入口时验证无环境即拒绝，不执行、不自动切换到其它身份。不能因手机未 Root 判定第四档验收失败，也不能以普通 APP 或 Linux guest UID `0` 代替 Shizuku。 |
| **iPA2475 平板** | 有 Root 环境 | **Operit 五档的第五档（最高档）：Root** | 由设备用户给隔离测试包授权后，`ROOT` 通过 App 自己的 `su` 路径实跑，核对实际 UID `0`、退出回执，以及要求的取消与审计。Shizuku 服务即使以 UID `0` 运行，也不能代替独立 `ROOT`。 |

## 如何使用

1. 开测前记录设备型号、系统/API、候选版本和隔离 APK 的安装读回摘要；再确认实际权限状态。手机的 Shizuku 未配对、未运行或未获授权时，需要完成第四档前置才能验收相应用例；不能用 Root 补齐，也不要求给手机提权。
2. 业务、数据、普通 `APP` 及已具备环境的 `LINUX` 等两机共同适用的用例，各自在同一候选上验证。设备条件不同的用例分别登记：平板提供独立 Root 正向证据，手机提供非 Root 的 Shizuku/ADB 正向证据及独立 Root 的安全拒绝。`不适用`单列，不计通过数；实际失败也不计不适用。
3. 只操作隔离测试包及合成数据，不触碰正式 App 或用户数据。记录命令实际 UID、退出码及取消结果，区分 Android 内核 UID、PRoot guest UID 和 App 内的一次性审批。
4. 用户授权本轮真机验收后，自动化完成已约定的设备流程，包括 vivo 安装确认及权限矩阵内的隔离包授权。确认前核对目标设备、包名、候选和当前弹窗，不把平板的 Root 正向条件套用到手机，不擅自扩大权限。系统无法自动完成且没有等价的合规路径时，记录具体阻塞，不将其计为通过。

这是验收设备的前置信息，不是各单元的通过回执，也不变更单元依赖或阶段出口要求。实施与验收结果按各轮交接记录。
